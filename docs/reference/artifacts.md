# Artifacts reference

Every file TestGuard writes, which command writes it, which schema validates
it, and whether it belongs in git. This page is for anyone setting up
`.gitignore`, wiring CI artifacts, or reading TestGuard's output with another
tool. Every JSON document below is validated against its schema before it is
written, so a file on disk is always one a reader can trust the shape of.

## The rule: commit the baseline, ignore the rest

The baseline is the frozen contract: which findings were already known when
you adopted a gate. Commit it, because a CI run on a fresh clone needs it to
tell new findings from old ones. Everything else under `.testguard/` is
regenerated by a run and describes one moment, so it does not belong in
history.

`testguard init` appends these lines to the project's `.gitignore`:

```gitignore
# TestGuard: regenerated per run (baseline.json IS committed)
.testguard/evidence.json
.testguard/evidence-provisional.json
.testguard/evidence-partial.json
.testguard/brief.json
.testguard/gate.json
.testguard/scaffold-*.json
.testguard/replay.json
.testguard/calibration.json
.testguard/ci-self-evidence.json
.testguard/ci/
.testguard/sweep.json
.testguard/sweep-evidence.json
```

Re-running `init` after an upgrade adds only the lines a newer release
introduced, directly after the ones already there, so the block never gains a
second header. The list is checked against the code: a test derives every path
a command writes under `.testguard/` and fails when one is missing here.

`testguard baseline` prints whichever of those git does not yet ignore, and
offers the form that needs no update when TestGuard adds an output. Both forms
ignore exactly the same files, and leave the same three trackable:

```gitignore
.testguard/*
!.testguard/baseline.json
!.testguard/status.json
!.testguard/fetch-ci-evidence.sh
```

If `.gitignore` already uses the `.testguard/*` form, `init` adds nothing. If
it ignores `.testguard/` as a whole, `init` leaves it alone and warns that
`baseline.json` should be committed.

## Files under `.testguard/`

| File | Written by | Schema | Git |
|---|---|---|---|
| `evidence.json` | `probe` (complete run, `--confirm` 3 or more) | [`evidence`](../../spec/schemas/evidence.schema.json) | ignore |
| `evidence-provisional.json` | `probe --confirm` below 3 | [`evidence`](../../spec/schemas/evidence.schema.json) | ignore |
| `evidence-partial.json` | `probe --claim`, `admit` | [`evidence`](../../spec/schemas/evidence.schema.json) | ignore |
| `baseline.json` | `baseline` | [`baseline`](../../spec/schemas/baseline.schema.json) | **commit** |
| `brief.json` | `brief` (not with `--text` or `--markdown`) | [`brief`](../../spec/schemas/brief.schema.json) | ignore |
| `gate.json` | `gate` | [`gate`](../../spec/schemas/gate.schema.json) | ignore |
| `scaffold-<basename>.json` | `scaffold <file>` | [`claims`](../../spec/schemas/claims.schema.json) | ignore |
| `sweep.json` | `sweep` | [`sweep`](../../spec/schemas/sweep.schema.json) | ignore |
| `sweep-evidence.json` | `sweep`, only when it probed something | [`evidence`](../../spec/schemas/evidence.schema.json) | ignore |
| `replay.json` | `replay` | [`replay`](../../spec/schemas/replay.schema.json) | ignore |
| `calibration.json` | `replay`, beside the replay document | [`calibration`](../../spec/schemas/calibration.schema.json) | ignore |
| `fetch-ci-evidence.sh` | `init --ci-evidence github\|gitlab` | shell script | **commit** |
| `ci/` | `fetch-ci-evidence.sh` (download directory) | n/a | ignore |
| `ci-self-evidence.json` | your CI, by convention (see below) | [`evidence`](../../spec/schemas/evidence.schema.json) | ignore |
| `status.json` | no command writes it | [`status`](../../spec/schemas/status.schema.json) | not ignored by either form; commit it if you keep one |

Every path above is the default; the commands that write a document take
`--out <path>` to put it elsewhere.

### evidence.json

One run's findings: every verdict, with every baseline run and probe run that
produced it, the resolved defenders and the files that mock the subject, the
input hashes that make verdict reuse sound, and the rank. It is the canonical
evidence: `status`, `baseline`, `brief` and the MCP tools read it. Only a
complete, confirmed run writes it, which is why a provisional or partial run
goes to its own file and can never be frozen into a baseline by accident.

The next `probe` reads its own output file to reuse verdicts whose recorded
inputs have not changed (`--no-reuse` turns that off).

### evidence-provisional.json and evidence-partial.json

`probe --confirm 1` or `2` writes the provisional file; `baseline` refuses it
unless you pass `--allow-provisional`. `probe --claim <ID>` and `admit` write
the partial file. Neither ever replaces `evidence.json`.

### baseline.json

The fingerprint of every non-passing finding at freeze time, with a count, the
commit it was taken at, and, when the evidence came from `--include-dirty`, the
snapshot commit. A fingerprint is `sha256(claimId \n subjectId \n file \n verdict)`:
derived from identity and outcome, never from the fault's text, so repairing a
rotted anchor does not churn it.

### brief.json

The same ranked, capped block `brief` prints, as text and as structured items.
The session-start hook uses `brief --text`, which prints and writes nothing.

### gate.json

Claim coverage of one change: changed, evaluated, excluded, covered,
uncovered, delegated to nested projects, the ignore entries relied on and the
expired ones, and the exit code.

### Scaffold drafts

A draft claims document for one source file, named after its basename without
the extension (`src/auth.ts` gives `scaffold-auth.json`). It is never your
claims file: statements are `TODO` placeholders. Move the claims you keep into
`testguard.claims.json` by hand.

### sweep.json and sweep-evidence.json

`sweep.json` holds what was swept, the selection arithmetic, the findings and
the draft claims documents the proposals came from (`drafts`), so you can keep
a draft without re-running the sweep. `sweep-evidence.json` holds the probed
records; the next sweep reads it, and `evidence.json`, to learn which fault
classes are productive in this repository. It is written only when something
was probed, because an empty document would teach the next run that every
class is unproductive.

### replay.json and calibration.json

The replay document lists each replayed fix commit with its verdict. The
calibration document gives, per fault class, the share of real escaped bugs
the suite missed, with a Wilson interval and the sample size; the validator
recomputes every number. `replay --out` moves both into the same directory.

### fetch-ci-evidence.sh

An on-demand helper written by `init --ci-evidence`. It runs from the project
it was written into, whatever directory you call it from, empties
`.testguard/ci/`, downloads CI's evidence for a branch (default `main`, or the
first argument) into it, and runs `brief . --text --evidence <file>` on the
first of `evidence.json`, `ci-self-evidence.json` or `.testguard/evidence.json`
it finds there. It uses the same CLI the session-start hook would:
`./node_modules/.bin/testguard`, then the repository root's
`node_modules/.bin/testguard`, then a `testguard` on `PATH`; never a package
runner. It exits `0` with a message when the platform CLI, a TestGuard CLI,
the artifact or an evidence file in it is missing. It is not a hook: the
session-start hook never touches the network.

| Variant | Needs | Downloads | Briefs from |
|---|---|---|---|
| `github` | `gh` | the artifact named `testguard-evidence-<branch>` | `.testguard/ci/evidence.json` (or `ci-self-evidence.json`) |
| `gitlab` | `glab` | the artifacts of the `testguard:probe` job | `.testguard/ci/.testguard/evidence.json` |

The `gitlab` variant matches the artifacts of the
[GitLab CI template](../guides/ci/gitlab.md). The `github` variant matches the
default-branch workflow in [GitHub Actions](../guides/ci/github-actions.md),
which uploads the action's `evidence` output under that name; the action does
not upload an artifact by itself.

### status.json

A name reserved for a snapshot of the status document. No command writes it,
and no ignore form TestGuard suggests ignores it: `init`'s per-file lines never
name it, and the `.testguard/*` form `baseline` advises negates it. If you want
a snapshot under review, write it yourself with
`npx testguard-cli status --json > .testguard/status.json` and commit it; it
describes the moment you wrote it, so refresh it in the same commit as the
change it describes.

### Files written outside `.testguard/`

| File | Written by | Git |
|---|---|---|
| `.claude/skills/testguard/SKILL.md`, `.claude/settings.json` (hook), `AGENTS.md` section | `init`, at the git root (or `[dir]` with `--here`) | commit |
| `.gitignore` lines | `init`, in `[dir]` | commit |
| `@claim` file-header comments | `claims --annotate --apply` | commit |
| a draft passed to `--into` | `scaffold --into` | your choice |
| `.testguard/brief.md`, `.testguard/post-note.mjs` | the GitLab CI template's probe job | CI artifacts only |

`claims --annotate --apply` and `scaffold --into` keep recovery copies of the
originals in an owner-only directory outside the checkout and report its
location.

While either one writes, it holds `.testguard-annotations.lock` in the project
directory: an exclusive, owner-only file naming the process that holds it. A
second writer refuses with `annotation authoring lock already exists` rather
than waiting. TestGuard never removes a lock it does not own, so one left by an
interrupted run stays until you delete it. Check that no TestGuard process is
still running before you do.

## Schemas

The shared formats live in [`spec/schemas/`](../../spec/schemas/), are JSON
Schema 2020-12, and are identified as `urn:claimspec:v1:<kind>`. The validator
is [`spec/lib/validate.mjs`](../../spec/lib/validate.mjs): it applies each
schema and then the rules a schema cannot express, such as unique IDs,
fingerprint derivation, N-run agreement and interval arithmetic.

| Schema | What it describes |
|---|---|
| [`annotations`](../../spec/schemas/annotations.schema.json) | The `claims --annotate` preview or apply result: targets, refusals and recoverable partial failures. Authoring, never verification. |
| [`authoring-input`](../../spec/schemas/authoring-input.schema.json) | The metadata-only report of `scaffold --from-document` or `--from-fix`. No source text, no claims. |
| [`baseline`](../../spec/schemas/baseline.schema.json) | Frozen fingerprints of existing findings, suppressed up to their count. |
| [`brief`](../../spec/schemas/brief.schema.json) | What to tell an agent before it writes code: ranked, capped, with the next action. |
| [`calibration`](../../spec/schemas/calibration.schema.json) | Per fault class, the observed miss rate with a Wilson interval and the sample size behind it. |
| [`claims`](../../spec/schemas/claims.schema.json) | The claims file, and every scaffold draft. |
| [`common`](../../spec/schemas/common.schema.json) | Shared definitions: verdict, fault class, severity, provenance, source kind, identifier, paths and dates. |
| [`concerns`](../../spec/schemas/concerns.schema.json) | The concerns file: scopes a sweep can be aimed by. |
| [`evidence`](../../spec/schemas/evidence.schema.json) | One run's records: verdict, every run, defenders, signals, input hashes, rank. |
| [`gate`](../../spec/schemas/gate.schema.json) | Claim coverage of one change. |
| [`ignore`](../../spec/schemas/ignore.schema.json) | The ignore file: reviewable scoping, every entry with a reason. |
| [`replay`](../../spec/schemas/replay.schema.json) | Replayed fix commits and whether the suite would have caught each. |
| [`status`](../../spec/schemas/status.schema.json) | Where the project is and the one next action; also the `--json` output of `probe` and `baseline`. |
| [`sweep`](../../spec/schemas/sweep.schema.json) | What a sweep proposed, probed and found, with its drafts. |
